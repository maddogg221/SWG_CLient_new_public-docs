# Technical Notes

A handful of illustrative notes and small fragments — enough to show real engineering rigor is behind this project, not a full walkthrough of how anything actually works. Deliberately incomplete by design.

## Verification discipline

Nothing gets marked "done" on the strength of it compiling or looking plausible against source code alone. The project's own working rule, applied consistently throughout:

> The wire is the source of truth — not the source code. Reference source shows what *can* exist on the wire; only real, captured traffic confirms what a live server actually sends.

In practice this means every decoder has, wherever possible, a permanent automated test built from **real bytes captured off a live connection** — not hand-invented sample data. The general shape of that testing style:

```cpp
TEST_CASE("<some message type>::parse - real captured payload") {
    auto buffer = bytesFromRealCapture(/* ... */);

    auto decoded = SomeMessageType::parse(buffer);

    CHECK(decoded.someField == /* the real, observed value */);
    CHECK(buffer.remaining() == 0); // no leftover, unexplained bytes
}
```

That last assertion — "no leftover bytes" — is treated as important as the field checks themselves: a decoder that reads the *wrong* number of bytes will usually still produce plausible-looking values, right up until the next message in the stream gets misaligned and everything downstream breaks. Catching that immediately, at the single point of failure, rather than as a confusing symptom three messages later, has repeatedly been worth the extra rigor.

## When source and reality disagree, reality wins

More than once, careful reading of reference source material led to a wrong conclusion that only real captured traffic exposed — including, this cycle, a case where a wire-format detail that looked ambiguous from source alone turned out to be fully resolvable once every layer that touches a message before this project's own code sees it was traced in full, not just the layer that seemed most relevant at first glance. The fix, once found, was confirmed three independent ways before being trusted — a deliberate, repeated pattern in how this project treats any conclusion it can't directly observe on the wire.

## A live cross-check that caught a real bug

The terrain generation work (see Progress) needed one thing no source-reading could provide: a real, independently-known "at this exact map position, the ground is at this exact height" fact to check the computed output against. That came from a live server telling the connecting client its own spawn coordinates directly — a value this project had been receiving and printing for a long time, but had never actually *used* for anything before.

Putting it to use immediately paid off: the raw values didn't line up with the computed terrain height at all, off by orders of magnitude, on a position independently confirmed to be standing on ordinary open ground. Rather than assume the newly-written terrain code was wrong, the reference source for that particular network message was re-examined end to end — and it turned out an internal helper on the *reference* side used two of its own axis labels in a way that didn't match the meaning this project (correctly, per every other position-carrying message already validated by rendering real objects on screen) had assumed. One message type had inherited that mismatch by naming its own fields after the reference helper's labels instead of their actual meaning — a mislabeling that had sat unnoticed because that particular value had only ever been printed to a log, never fed into anything that would have visibly disagreed with reality.

Fixed, then re-verified against two independent live servers: computed height matched real ground height to well under a meter both times, with a deliberately-included "standing inside a building" sample confirmed to *not* match — proof the test itself was discriminating, not just always agreeing.

## A small, honest example of graphics-side rigor

The rendering pipeline's real-geometry shading uses a standard, well-known technique (half-lambert shading) rather than anything exotic — the point was never to reinvent graphics, only to get real objects on screen correctly and quickly:

```hlsl
float shade = 0.5 + 0.5 * saturate(dot(normalize(worldNormal), lightDir));
```

Small, boring, and correct — which is the actual goal at this stage of the project.

## A compressed-format ambiguity that only got resolved by reading the real client's own code

Character animation data is stored using a well-known compression trick for unit quaternions (often called "smallest three"): rather than store all four rotation components, the encoder drops whichever one has the largest magnitude and stores only the other three, quantized. On decode, the dropped component is reconstructed mathematically from the other three via `sqrt(1 - x² - y² - z²)` — a square root, which has two possible signs, only one of which is the rotation the encoder actually intended.

General background research into this technique suggested the decoder needs some extra signal to pick the correct sign — and a first implementation was built on that assumption, disambiguating frame-to-frame using a global optimization pass that picked whichever sign kept a whole animation channel's motion smoothest. It mostly worked, but not always: certain limbs would intermittently snap into a wildly wrong orientation for a frame or two, in a way no amount of tuning the smoothness heuristic fully eliminated.

The actual answer turned out not to be a smarter disambiguation algorithm at all. Reading the relevant decode routine directly in the original game client's own compiled code showed it does no sign check whatsoever — it takes the plain, unconditionally non-negative square root, every time, full stop. The encoder guarantees this works by choosing, at export time, whichever overall sign of the quaternion (`q` or `-q` — both represent the identical rotation) makes the dropped component come out non-negative, so the decoder never has anything to guess. The general "smallest three" technique doesn't inherently require this convention, but this particular content pipeline does — a detail no amount of reasoning about the compression scheme in the abstract was going to surface, and that no amount of statistical tuning against sample data fully compensated for either. Only reading the real, authoritative implementation settled it, and once applied, an entire category of intermittent bad-frame artifacts went away at once rather than needing to be chased individually.

Finding that routine at all, inside an executable with no symbols and no source, is its own small story. The way in wasn't guessing at addresses or scanning for byte patterns first — it was searching the binary for human-readable debug strings the original developers had left baked into it (an internal class name logged during setup, in this case), then reading outward from that one confirmed landmark: what constructs this, what else references its name, what does the code actually do a few calls downstream. Most of what that trail turns up first is boilerplate — constructors, reference counting, object-pool bookkeeping — that has to be recognized and set aside rather than mistaken for the real logic. The actual arithmetic, when it was finally reached, was a handful of floating-point instructions doing exactly the multiply-add-square-root sequence the math predicted, which is its own satisfying confirmation of being in the right place. Slow, methodical, and a genuinely different kind of puzzle from the network-protocol reverse engineering this project otherwise does daily — closer to archaeology than to decoding a spec.

## Finding a live graphics-API address in a binary with no import table to read

A recurring problem when reading a compiled game client directly: modern graphics APIs like Direct3D are accessed entirely through interface objects handed out at runtime — there's no fixed address for "the function that draws a triangle" sitting in the executable waiting to be found by name. The object implementing the graphics device doesn't exist until the game creates one, and every method call on it goes through a table of function pointers whose *layout* is a documented, stable public contract, but whose actual in-memory *location* is different every time the program runs.

The general technique that worked, reusable for any similar API: catch the one moment the graphics device gets created (this only happens once, early, so the debugger has to be attached from process launch rather than to an already-running instance), capture the object handed back at that exact moment, then read its function-pointer table directly out of memory using the *public, documented* method ordering for that interface — no internal knowledge of this specific game required, just the same publicly available interface contract any graphics programmer would already have. From there, the address of any method on that interface — draw calls, state changes, resource creation, anything — is a single, deterministic memory read away, and stays valid for the rest of that run.

This turned a category of "there's no symbol for this, so it's effectively unreachable" problems into "there's no symbol for this, but the address is still fully computable" — a meaningfully different, much more tractable situation.

## Ruling things out is still real progress

A specific, real question came up while investigating how animated characters actually get drawn: does this client compute skinned character poses on the CPU (composing each bone's position and writing final vertex data before anything reaches the graphics card), or does it hand raw pose data to the graphics card and let it do that math on every vertex during rendering? The two approaches lead to genuinely different places to look for how a character's final shape gets built each frame, so getting this right mattered before going further.

The direct way to test it: watch every place the client uploads per-vertex transform data to the graphics card during a real play session, and see what's actually being uploaded. Doing this live turned up a real, if slightly deflating, pattern at first — three different, independently traced call sites, each fully followed back to its origin, and each turned out to be something else entirely: one was ordinary camera/viewport setup, one was a level-of-detail selection routine picking among nearby quality tiers based on view distance, and one was a generic per-object "this became newly visible, refresh its pending state" mechanism that applies uniformly to every kind of object the engine renders — buildings and trees included, nothing specific to characters at all.

None of those three were the answer, but ruling each one out *was* the answer forming: a real, named class in the client's own code — one whose very name describes exactly this ("software" being the standard industry term for CPU-side computation, contrasted with the graphics card doing the equivalent work) — turned out to be responsible for skinned characters specifically, and tracing one of its real operations through to completion led all the way to an actual, ordinary "draw these triangles" graphics-card call, using geometry that had already been fully assembled by the time it got there. That's about as direct a confirmation as reverse engineering this kind of thing gets: not an inference from absence, but watching the real handoff happen.

The methodological point worth keeping, independent of the specific answer: a wrong-looking result that's been fully, honestly traced to its actual cause is worth more than a plausible-sounding guess left unverified, even when — especially when — the traced result isn't the one being hoped for going in.

## An experimental fix that a live-code read proved unnecessary

A real, visible animation artifact on articulated character geometry — a flat, collapsing seam at certain joints — led to trying a well-known alternative blending technique specifically designed to eliminate that class of artifact, on the theory that the more common, simpler blending approach was the inherent cause. It was a reasonable theory: the artifact matched a textbook description of that simpler approach's known failure mode closely enough to justify the experiment.

Reading the real client's own compiled code settled it differently. The official implementation uses the plain, simpler blending approach — not the more sophisticated alternative the experiment had switched to. If the simpler approach's known failure mode were really the cause, the official client would show the same artifact under the same conditions, and it doesn't. That's a clean, falsifiable test: the theory predicted something checkable, and reading the real implementation checked it directly rather than continuing to guess. The experimental change was reverted in favor of matching the confirmed real technique, and the search for the actual cause narrowed to something else — not the blending family, but somewhere in the underlying per-joint data feeding it.

The broader point: an experimental fix that make a symptom look different isn't the same as a fix that addresses the real cause, and the fastest way to tell the two apart, when the ground truth is available at all, is to go read it directly rather than keep iterating on the symptom.

## Knowing when to stop chasing a root cause and fix the data instead

A follow-up investigation into that same joint artifact went looking for ground truth more directly — tracing how the official client actually manages the memory it writes finished per-vertex data into, frame by frame. That trace turned up a lot of real, working detail: a resource-pool allocator identified by name via a debug string baked into the binary, the specific method responsible for handing back a writable buffer, and a ring/bump-allocator pattern managing where in a shared arena each frame's data actually lands.

What it didn't turn up, after a long session, was the literal values being written — the actual numbers needed to compare directly against this project's own computed output for the same joints. Getting there would have meant reliably capturing several different pieces of fast-changing, live process state at the exact same instant, by hand, through a slow manual read-and-record workflow — and two separate attempts at that hit the same wall: values read a few steps apart in time turned out to be already inconsistent with each other by the time all of them were in hand.

Faced with that, the practical call was to stop pushing on the reverse-engineering thread for the moment and go fix the actual defect a different way: directly reworking the affected geometry's own per-vertex weighting using existing, community-built asset tooling, rather than continuing to chase the official client's exact internal arithmetic. This doesn't require ever learning the precise root cause — it repairs the specific broken data directly, and can be checked against the same live rendering used throughout. If a cleaner way to capture multiple pieces of live state atomically turns up later (scripted, rather than manual, capture is the obvious next tool for that), the deeper question is still worth returning to — but shipping a real fix didn't need to wait on it.

## When the trail keeps leading to shared, generic code

A follow-up to the CPU-vs-GPU skinning question above: on the actual hardware this project tests against, the CPU-side ("software") skinning class turns out not to run at all — extensive real play, including several minutes of continuous character movement and multiple full zone transfers, produced zero hits on it. That's a real, useful negative result on its own: it means the graphics card is doing that math instead, which points the investigation somewhere new — toward whatever mechanism hands per-bone transform data to the graphics card for it to apply per vertex.

The obvious candidate is a well-known, standard technique: upload a batch of transform values to the graphics card as shader constants once per frame, sized to match however many bones a given character's skeleton has. Watching every real call that uploads shader constants during actual animated gameplay — over 150,000 of them, captured live — settled that question cleanly: none of them were remotely large enough. The biggest single upload seen was a small fraction of what a real bone-matrix batch would need. Whatever this client does instead, it isn't that.

That pushed the search toward a different, less certain lead: a lower-level buffer-locking operation, confirmed real and actively used, that looked like a plausible place for finished per-vertex data to get written directly. Watching *that* operation instead told a different story — the gap between consecutive real calls to it varied wildly in size, and reading the actual bytes sitting at a few of the addresses it touched turned up things with nothing to do with character geometry at all: a fragment of a human-readable tool/version string in one case, a recognizable "this memory was never actually written, or was already freed" fill pattern in another. That's the signature of a genuinely generic, engine-wide utility — shared by terrain, UI, and probably dozens of other systems — not a dedicated per-character-skinning code path. Watching it without a much narrower filter can't isolate the one thing being looked for.

Neither of those two leads panned out, but each rules something concrete out, the same way the software-vs-hardware question did earlier. The instinct to treat a generic-looking hook with suspicion — and to actually read what's really there rather than assume a plausible-looking call site is the right one — has paid off more than once on this project now; it's becoming a standing rule rather than a one-off lesson.

## A safety lesson from trying to make the debugger drive itself

Most of this project's binary-level reverse engineering happens through a live, interactive debugger session, with a person relaying what's on screen back and forth — accurate, but slow. It's a reasonable engineering instinct to want to automate that: have the debugging tool run unattended, scripted, reading its own output directly instead of going through a human relay each time.

One attempt at that, using a legitimate, official command-line debugging tool in its supported "run as a background service" mode, caused the entire machine to lock up hard enough to require a full reboot — twice, on two separately-designed, increasingly cautious attempts. The second attempt deliberately avoided everything that seemed risky about the first (no following child processes, no manual process-backgrounding tricks, attaching to an already-stable process instead of launching a fresh one) and still failed the same way. That's worth stating plainly rather than glossing over: a tool being official, well-documented, and used carefully is not the same as a tool being safe to use in every configuration, on every machine — and two independently-designed attempts failing identically is a much stronger signal than one.

The concrete lesson, kept for next time: when a new piece of tooling causes a failure with real, disruptive consequences, the right response isn't "try again more carefully" — it's stop, write down exactly what was tried and what happened, and treat the whole approach as unsafe on this setup until there's a genuinely different plan, not just a more cautious version of the same plan. The underlying goal (less manual relay, more direct automated inspection) is still worth pursuing eventually; it just needs a different implementation than the one that already failed twice.

## A well-known visual quirk turns out to be a real, deliberate design choice

The original game is well known among people who've played it for a distinctive look to character hands: fingers barely move independently, giving a stiff, "wearing mittens" impression during normal animation. A reasonable question came up while chasing an unrelated animation defect in this project's own reimplementation of the same content: did the original developers run into the same category of difficulty this project has been wrestling with, and simply lock some fingers together as a pragmatic simplification rather than ever fully solving independent finger articulation?

Trying to confirm that through general research came back inconclusive — worth saying plainly rather than presenting it as more certain than it is. But the real, shipped character skeleton data this project has already extracted settled the question directly and immediately: a human hand has five digits, but the actual skeleton defines independent, fully-articulated bone chains for only two of them. The remaining three fingers share a single driving bone between them. That's not a gap in how this project reads the file format — every bone in the skeleton was enumerated and checked. The original riggers built it this way on purpose.

That single fact retroactively explained something noticed much earlier and, at the time, just filed away as an unremarkable detail of how the source mesh happens to be authored: the overwhelming majority of vertices on this exact hand model are rigidly bound to one single bone each, with no blending between adjacent bones at all. Once the three-fingers-one-bone structure was understood, that stopped looking like an unremarkable detail and started looking like its direct, necessary consequence — there's nothing to blend between influences on a mesh region if it was only ever built to move as a single rigid unit in the first place.

It also generated a genuinely new, sharply testable idea for the unrelated defect this investigation started from: a vertex bound rigidly to exactly one bone can't visually tear away from its neighbors on its own, no matter how wrong that bone's own computed position might be — tearing specifically requires *disagreement* between vertices bound to *different* bones. If that reasoning holds, whatever's actually broken should be concentrated on the two fingers that really do have independent, blended articulation, and should be entirely absent from the merged three-finger mass, which should stay solid — stiff and simplified-looking, matching the original game's own known appearance, but not torn. That was a real, falsifiable prediction — worth checking directly rather than trusting on reasoning alone.

Checking it directly, the same session, turned out to only be half right, which is worth reporting as plainly as the rest of this: a close, per-bone color-coded render confirmed each individual finger's own geometry does stay internally compact, exactly as the "a rigid group can't tear itself" reasoning predicted. But the *specific* prediction that the rigid three-finger mass would stay solid while only the independently-articulated fingers stretched did not hold — the rigid mass displaced just as far as the others did. That rules something out just as concretely as it would have if the prediction had succeeded: whatever's actually wrong isn't specific to blended-weight vertices at all, since a rigid region showed the identical symptom. It points back toward how each bone's own position gets computed relative to its parent, uniformly, rather than anything to do with how a mesh's vertices are weighted to it. A prediction that fails cleanly is still a real result, not a wasted one — it closes off an entire category of explanation just as effectively as a confirmed one would have opened a new path.

## Checking that two things actually agree, instead of assuming it

An earlier investigation into the same joint-animation defect discussed above had concluded that this project's own reimplementation and a separate, independently-built reference tool were both computing the same wrong result — reasonable grounds, at the time, for suspecting the shared underlying approach rather than either specific implementation. A direct, careful numeric comparison between the two, done properly this time — comparing real computed values bone by bone down an actual affected chain, not just eyeballing that both looked equally wrong — told a different story: the two implementations actually disagree with each other, and disagree starting at a specific, identifiable point.

Tracking that disagreement down found a real, ordinary bug in the reference tool's own code: a bone with no animation data in the particular clip being tested was silently left at a default, un-rotated pose instead of applying the fixed offset rotation it should always have, animated or not. A completely different, unrelated defect from the one originally being investigated — but one that had been quietly making an earlier conclusion look more solid than it actually was, because two different implementations that both happen to show *some* visible distortion look, at a glance, like they agree.

The corrected comparison also produced a genuinely useful positive result: measuring real bone-to-bone distances directly out of this project's own computed output — not compared to anything else, just checked against known real anatomical proportions — showed every single segment coming out exactly correct, at multiple points in the animation, with no stretching anywhere in the skeleton itself. That's a meaningfully different, better-supported place to be than "probably somewhere in this shared approach": the skeleton's own math is now positively confirmed correct, which redirects the remaining search toward other, more specific candidates instead.

The lesson, worth keeping independent of this specific bug: "two systems produce a similarly broken-looking result" is not the same claim as "two systems agree," and treating them as equivalent risks locking in a wrong theory of the cause. Checking real, specific values against each other directly — not just comparing overall impressions — is worth doing before trusting a conclusion built on "these two things must share the same problem."

## Closing the gap between "the math checks out" and "it still looks wrong"

Verifying that one specific piece of a pipeline is correct is not the same claim as verifying the whole pipeline is correct, and it's worth being precise about the difference rather than letting a partial result quietly stand in for a complete one. Having confirmed the skeleton's own joint positions were correct, the next real question was whether that same confidence extended to the following step: taking those correct joint positions and actually applying them to a mesh's real vertices.

It didn't, and the only way to find that out for certain was to stop reasoning about the code and run it — the actual function the live game calls, on the actual extracted vertex data, producing real numbers to check against a known-correct reference size. The result was unambiguous: vertices that should form a hand a little over a hand's-width across came out spanning most of a full body-length instead, and the size of that error grew directly with how far the character's pose had moved from its rest position — a real, measured relationship, not a guess. That's a meaningfully different, more useful place to be than before: not "something in this whole system is wrong," but "specifically the step that maps a rest-pose vertex onto its currently-posed bone."

A first concrete guess at the specific mechanism — building that mapping from a plain, un-corrected rest skeleton rather than the joint-orientation-corrected one currently used — was tested the same direct way and made the result worse, not better, cleanly closing off that particular idea rather than leaving it as an open, untested guess. The real mechanism isn't found yet, but the difference between "haven't found it" and where this investigation started is significant: the search now has a known-correct half of the pipeline, a precisely measured symptom, and one ruled-out theory, instead of an open-ended question spanning an entire animation system.

## When an entire category of explanation turns out to be the wrong category

After decisively narrowing a stubborn animation defect down to one specific step in the pipeline (see above), the obvious next move was systematically testing every reasonable variation of the math at that step - different orderings, different reference conventions, the handful of alternative formulas that are the standard textbook options for this kind of problem. All of them were tested properly, one at a time, against a precise real measurement rather than eyeballing a render - and none of them worked. Not "one worked a little better," genuinely none.

That's a useful result on its own, but the more useful move was noticing what it implied: if a dozen reasonable variations of the same formula all fail the same way, the formula itself probably isn't the problem - the assumption underneath all of them might be. So instead of trying variation thirteen, the next check tested that underlying assumption directly: does a specific point on the character model actually sit near the joint that's supposed to be moving it?

It didn't - not by a small margin, but by a distance close to the character's entire height, and by almost exactly the same amount for several different points on completely different fingers. A consistent, uniform offset like that isn't what a wrong rotation formula produces; a wrong formula's error tends to grow or shrink depending on how much the joint has rotated. A flat, constant mismatch instead points at something much more basic: two pieces of data that are each individually fine, describing positions measured from two different starting points, being combined as if they shared one.

The specific mechanism behind that mismatch isn't confirmed yet, but the shape of the investigation changed meaningfully: instead of continuing to search inside a category of explanation that had now been thoroughly exhausted, there's a concrete, different, and much more promising direction to check next.

Checking further the same session sharpened that finding into something more precise than the first read suggested. The initial framing — two datasets disagreeing about where "zero" is — implied the mismatch should show up everywhere equally. Running the same check across every separate body-part piece the character is assembled from told a different story: the torso, legs, and head all check out close to correct. Only the arm chain shows the large mismatch, and it grows steadily the further out from the shoulder it's measured — small at the elbow, largest at the fingertips. That's a meaningfully different shape of clue than "two coordinate systems don't agree": a limb whose base is roughly right but whose end is increasingly wrong looks much more like "the assumed resting position doesn't match the pose this content was actually built against" than "the numbering scheme is offset." Torso and legs barely move between different reasonable resting positions; an arm's resting position varies a great deal depending on the convention used, which is exactly consistent with only the arm being affected, and increasingly so with distance from the body. Worth recording as its own small lesson: the first shape a finding takes isn't always its most useful shape — checking it against more of the same kind of data, rather than stopping at the first passing explanation, is what turned a vague "something disagrees" into a specific, checkable claim about which one thing is actually assumed incorrectly.

A few more concrete guesses at what the correct resting position actually is were each checked directly and each came back negative: using a real early frame of actual animation data instead of a synthesized neutral pose made no difference; a small wrapper file that names which detail-level mesh to load turned out to carry no positioning information at all; and a full scan of every named animation state this content defines turned up nothing resembling a dedicated reference or bind pose among them - only ordinary gameplay state names. A real, actively-used piece of community-built tooling for this same content was also checked directly on the chance it had already solved this exact question - it hadn't, because it turns out to operate one level higher than this problem: it imports raw mesh geometry only and expects a skeleton to be supplied separately, so it was never actually attempting the specific alignment being investigated here. Ending a long, genuinely thorough elimination pass without the answer isn't the same as ending without progress - every plausible nearby explanation checked today is now confirmed not to be it, which is exactly the information needed to know where to look next.

## A real discovery that still ended in a dead end, reported as such

Picking the resting-pose investigation back up through the official client's own compiled code turned up something genuinely real along the way: a confirmed, named, standard-library-style function that combines two spatial transforms together, one of which turned out - once traced byte by byte - to be a scale-only transform built from three separate numbers, folded into an attachment calculation via ordinary matrix multiplication. That's a real, previously unknown-to-this-project mechanism, not a guess: object scale, applied to an attachment point, through completely ordinary and identifiable math.

It came from following a real, promising-looking piece of the client's own code - attachment points for things like held items - on the reasonable theory that it might be the same mechanism responsible for how a character's individual body-part meshes get positioned relative to their skeleton. Two direct, real tests settled that it probably isn't: a breakpoint on the exact function in question didn't fire during ordinary standing, and didn't fire when actually equipping and re-equipping an item live in the running game either - the two most obvious moments that code should exist to handle, if it were the right code.

Worth recording plainly rather than treating as wasted effort: a real, verified fact about how the client works came out of this (the scale-via-multiply mechanism, which may turn out useful for a different question later) even though the specific hypothesis it was found while chasing didn't pan out. Two negative results from direct testing are worth more than one untested guess left sitting unresolved, and saying so honestly - rather than quietly moving on - is what keeps the next attempt at this same problem from re-treading the same ground.

## A fix that looked strong on paper and failed the moment it mattered

A long-running animation defect finally produced a testable idea: instead of trusting a separately-authored reference position to correctly describe where a body part sits at rest, derive that resting position directly from the actual mesh geometry itself - measured, not assumed. Checked against a standalone, isolated test, the results were genuinely convincing: a badly-distorted measurement dropped to within a hair of the known-correct value, and stayed there consistently across a full cycle of sampled animation frames. Every existing automated test still passed. By every offline signal available, this looked like the fix.

It wasn't. Run for the first time inside the actual running game against a live server, the result was worse than the original defect - not merely still wrong, but broken in a new and more severe way, with part of the affected geometry visibly tearing into disconnected floating fragments rather than the milder continuous distortion seen before. The most likely explanation, worked out afterward: the correction had been computed independently for each small structural piece, with nothing to keep neighboring pieces' corrections consistent with one another - so while each individual piece moved closer to being individually correct, adjacent pieces could easily end up pulled in incompatible directions relative to each other, tearing the seam between them instead of closing it.

The sharper lesson is about the offline test itself, not just the fix: it validated a single aggregate summary number (an overall bounding box) on only one of two symmetric structures that needed the same treatment. That kind of measurement can look completely clean while hiding exactly the local, piece-to-piece inconsistency that turned out to matter most - and it never got the chance to catch the fact that the second, untested structure behaved substantially worse than the first. The fix was reverted immediately once the live result was seen, rather than left in place because the offline numbers had looked good. A test that only checks an aggregate outcome, on only half the real cases, isn't validation - it's a coincidence waiting to be exposed by the one condition it didn't check.

A second attempt, the same session, fixed the specific mechanical flaw identified above and validated far more rigorously - both symmetric structures this time, across multiple points in the animation, plus a genuinely new check specifically designed to catch the exact failure mode from before (measuring the gap at every seam between adjacent pieces, not just the overall silhouette). Every one of those checks passed cleanly. It still failed live - by direct, first-hand report, worse than the original attempt, with major structural pieces no longer even connected to each other. The real cause, understood only afterward: the correction was being computed separately for each independent chunk of the character rather than once, consistently, across the whole structure - so pieces that shared a common attachment point could each end up with a different, incompatible idea of where that shared point actually was. Nothing in either round of testing had ever checked for agreement *between* separately-computed chunks, only correctness *within* each one on its own.

Worth stating plainly: assessing a screenshot of the live result and reporting it as fine, when the person actually looking at the moving, rotatable scene said otherwise, was a real mistake - a single flat image from one angle is strictly weaker evidence than direct, live observation, and treating it otherwise nearly let a confidently-wrong read stand in for the truth.

## A long-running defect, finally resolved, and the real lesson underneath it

The animation defect described in the two entries above stayed open across many further sessions of careful, methodical testing - every reasonable hypothesis about the composition math, several independently-designed fix attempts, each validated as rigorously as the last one's failure suggested was needed, each still wrong in a new way once actually run live. At some point the honest question stopped being "which variation of this formula is correct" and became "is this even the right category of explanation at all."

The breakthrough didn't come from another round of formula variations. It came from getting access to genuine historical reference material for how this platform's original tools actually worked, and reading it directly rather than continuing to infer it from behavior alone. That material pointed toward one specific piece of previously-unread data this project's own parser had never consumed, and toward the exact real formula for combining it with data that already was being read. Implementing that formula honestly did not, by itself, turn out to be the fix - offline verification against real animated data showed it disturbing parts of the render that already looked correct, not just the part that was actually broken, which is exactly the kind of red flag worth stopping and investigating rather than shipping on optimism.

Chasing that red flag down produced the actual answer, and it wasn't the formula at all: a plain byte-ordering mistake in how a single category of rotation data had always been read from these files - the components stored in one order, read back in a different one. The way this was finally isolated is worth recording as its own lesson. A single measured discrepancy, on its own, could have meant almost anything. What made it diagnosable was noticing that the *same* discrepancy, of the *same* size, showed up independently across dozens of unrelated skeletal joints - not a plausible outcome for dozens of real, independent errors, but exactly the fingerprint of one systematic misreading applied uniformly everywhere. Once that pattern was trusted over the more exciting-sounding "found the missing formula" explanation, checking the actual byte order directly against the original real source confirmed it in minutes.

It also explained something that had been sitting in this project's own records for a long time without a satisfying explanation: why the defect was always confined to one specific limb chain while the rest of the body consistently rendered correctly. Whenever a joint's own data happened to be symmetric, the ordering mistake canceled itself out by pure coincidence, producing a correct-looking result for the wrong reason. Only joints with genuinely asymmetric data were exposed - which is precisely the shape the defect had shown from the very first session anyone looked at it, years of the project's own timeline earlier. The clue had been accurate the entire time; it simply pointed at the wrong mechanism until the right piece of ground truth was available to check it against.

A second, related defect - fingers curling away from the palm instead of into it - resolved immediately afterward using the same "verify against real data, then trust a live result over an assumption" discipline: a direction/sign convention already known to be necessary for most of the body turned out to need the opposite treatment for exactly one specific chain, confirmed by direct live comparison rather than reasoning about it in the abstract.

Both fixes are live-verified against a real running server, not just reasoned about: a full character body, including hands and fingers, now renders as a single connected, correctly-proportioned shape instead of the torn, disconnected geometry every earlier attempt in this project's history had produced.

## A flat lookup table turned out to be the wrong mental model entirely

Once individual character poses were rendering correctly (see the long defect saga above), the next step was picking *which* pose or motion to show for a given situation — standing, walking, and so on. The first implementation assumed the simplest reasonable structure: a lookup table from situation name to a single animation file, built by scanning the relevant content file and taking whatever it found. It worked well enough for straightforward cases to seem basically right.

It wasn't. Certain situations started resolving to visibly wrong content — the wrong style of motion entirely, or content clearly intended for a different character gender than the one being rendered. That's not the kind of bug a person can reason their way out of by staring at a lookup table; it meant the mental model of "one situation maps to one file" was itself incomplete, and the only way to find out how was to read the actual file structure directly, byte by byte, rather than trust the simplifying assumption further.

The real structure turned out to be a small recursive decision tree, not a flat table at all: a situation can resolve through a named-parameter switch (gender being one real example — the same situation name legitimately branches to different content depending on which character is asking), which can itself contain a container mixing a further sub-switch with situational variants (a locomotion-tagged option living alongside an otherwise-unrelated idle option, for instance), which can in turn wrap an outer "pick one of several weighted variations" layer before finally reaching an actual leaf clip. None of that nesting is optional or an edge case — it's the normal shape of the format, and a parser that only ever reads the first thing it finds at the top level will silently produce a plausible-looking but wrong answer more often than it might seem, because "plausible-looking" and "correct" only reliably coincide once every real layer is actually walked.

One specific wrong turn along the way is worth recording honestly: an intermediate heuristic assumed that, when a switch offered multiple branches with no other obvious tiebreaker, the branch carrying the least extra situational metadata was probably the sensible default. Tested directly, it wasn't — it landed on a genuinely unrelated piece of flavor content (built for an entirely different, situational use) instead of the intended everyday default. The fix wasn't a smarter tiebreaker; it was recognizing that some of these branches need to be identified by real content fingerprints (in this case, gender-specific naming baked into the referenced files themselves, checked across the whole branch rather than just its first entry) instead of guessed at structurally. Once the parser walked the real tree shape and used a real, content-based signal to resolve the one genuinely ambiguous branch, selection became reliable across every situation checked.

## When a defect can't be described, it has to be measured instead

Some defects are easy to characterize precisely in words — "this value is off by exactly this much." Others plainly exist, are immediately obvious watching the character move live, and are still remarkably hard to pin down through description or a still image alone. A walk-cycle defect fell squarely into the second category: watching it live, something about the way the legs moved read as wrong — exaggerated, occasionally looking like the legs crossed each other — but repeated attempts to characterize that precisely from screenshots kept missing the actual problem, because a single frozen frame from one angle just doesn't carry the information a moving, continuous gait does.

Rather than keep iterating on descriptions of a moving picture, the approach changed to something that doesn't depend on describing anything at all: pulling real numbers directly out of the character's own computed skeleton while it was actually walking against a live server, and checking them against simple, objective, anatomical facts a correct gait has to satisfy — does a knee bend the direction a real knee bends, do the left and right legs actually alternate rather than moving in lockstep, does either foot's position ever cross to the wrong side of the body's own centerline. None of that requires anyone to describe what something "looks like"; it's just arithmetic on real, already-computed positions, checked while the defect is actively happening.

One of those checks initially produced a striking, almost too-convincing result: the character's own central reference point appeared to be rotating by tens of degrees within a single stride — far beyond what a real human body does while walking in a straight line, and exactly the kind of large, obviously-wrong number that's tempting to treat as the answer. It wasn't. Testing it directly, by disabling the specific mechanism that number seemed to implicate and watching the live result, changed the character's standing posture but did nothing at all to the walking defect — a clean, immediate negative result. The likely real explanation, on reflection: that measurement compared each moment only against a single snapshot taken once at the start, with no way to distinguish an actual animation bug from the ordinary, entirely legitimate effect of the player deliberately steering the character's facing direction with the mouse while walking. A number that looks dramatic isn't automatically the cause — it has to survive an actual, direct test against the live system before it earns that status, and this one didn't.

A second, smaller lesson came from the diagnostic tooling itself, not the animation: an early version of one of these checks measured a limb's position from the wrong anatomical reference point — the joint nearest the body's center, which barely moves during a stride, rather than the joint at the far end that actually swings. The result was a suspiciously frozen, identical number reported over and over, which is its own kind of tell: real motion doesn't produce perfectly static measurements, so a diagnostic reporting one is usually broken, not reporting a genuinely motionless system. Worth remembering as a general rule for building this kind of live instrumentation: an unchanging number from something that's visibly moving is far more likely to mean the measurement is wrong than that the underlying system is somehow frozen.

None of the geometric checks tried this way found an anomaly — by every one of those measures, the underlying skeleton math looks like a plausible real gait. That's genuinely useful information even without a fix in hand: it makes a wrong-formula or wrong-sign bug in the joint math itself considerably less likely as the explanation (a different, earlier defect in this same animation system did turn out to be exactly that kind of bug, and showed a very different signature when measured this way), and it redirects the remaining search toward the mesh geometry and how it's bound to those joints instead — including one concrete, measured data point worth keeping: at the closest point in a real sampled stride, the two legs' corresponding joints passed within a few centimeters of each other, close enough that simple mesh thickness alone could plausibly explain a visual "crossing" impression with no error in the joint angles at all. The underlying defect isn't fixed yet, but the search is now aimed at a meaningfully narrower, better-evidenced target than "something about the legs looks wrong."

## When the numbers run out, build a way to actually see it

The numeric checks described above ran out of leads without finding the cause — every objective, arithmetic test of the walk cycle's joint positions came back clean. That left a real methodological problem: the defect was still plainly visible watching the character move, but neither careful description nor a battery of geometric checks had explained it. The next step was to stop trying to describe or measure the *symptom* and instead build a way to directly *see* the same thing side by side with a trustworthy reference.

That meant adding a real capability to the project's own client: the ability to lock the camera to a fixed, repeatable angle relative to the character and capture a rapid burst of exact frames to disk, rather than relying on whatever a screenshot happened to catch. Paired with a handful of comparable frames captured from the original game at matching angles, the two could finally be viewed directly against each other — the first time in this whole investigation that the comparison was a real picture instead of a memory or a written description.

That direct comparison overturned the leading hypothesis from the numeric-only phase. The earlier working theory — that the defect lived in how the character's mesh geometry was bound to its skeleton, since the joint math itself measured clean — turned out to be a reasonable but incorrect inference from incomplete evidence. Side by side, the real difference was plain: the reference gait takes a short, contained stride, while this project's own version reaches noticeably farther on both the legs and the arms. Viewed from straight on, an overly long stride naturally reads as a "crossing" silhouette purely from ordinary foreshortening — which is exactly the impression that had been driving the investigation for so long, without ever being the real geometric fault the numeric checks were searching for.

Checking the raw recorded rotation values for the leg joints directly confirmed they aren't the problem either — the values themselves fall within a plausible range for real human movement. That leaves the most likely remaining explanation not "a wrong number was recorded" but "the recorded numbers are being combined incorrectly on the way to a final pose" — a meaningfully narrower, better-defined target than either of the two hypotheses that came before it, arrived at only once the comparison could actually be *seen* rather than reasoned about secondhand.

The same side-by-side capability immediately answered a second, older, previously-unconfirmed question too: the character's resting stance had been suspected for a while to differ from the original game's, based on a description from someone with a great deal of hands-on familiarity with the original — but had never been checked directly. It does differ, visibly and unambiguously once the two images sit next to each other: the reference stance holds its arms loosely at the character's sides, while this project's version holds them out and away from the body. A gap that had lingered as an educated guess for a while became, the moment a real comparison was possible, an unambiguous, confirmed defect — not yet fixed, but no longer a question mark either.

## Checking an assumption against the people who actually built it

A recursive content-selection format decoded earlier (see "A flat lookup table turned out to be the wrong mental model entirely," above) had one piece deliberately left as an educated guess: when a branching choice in that format needed to be resolved for a specific character (which of two content branches applies to this particular individual), no directly observed rule existed for making that choice, so a heuristic was built instead — scan every real file referenced anywhere under each branch for a content fingerprint hinting at which branch the choice was actually meant for. It worked reliably on every real case tried.

Genuine historical reference material for how this platform's original content pipeline actually worked later became available, and it settled the question directly rather than by further guessing: the real mechanism is a straightforward table mapping a specific known value to a specific branch, with an explicit fallback entry for anything not found in that table. Reading that mechanism confirmed something important on its own — the overall recursive, branching shape this project had already reverse-engineered from raw file bytes alone matched the real, authoritative structure exactly. Independently arriving at the correct shape of an undocumented format, purely from evidence, and then having it confirmed by genuine reference material, is a meaningfully stronger kind of validation than either source alone would provide.

It also produced a genuinely humbling, worth-reporting-honestly wrinkle. Implementing the real table-lookup mechanism and then checking it against a large batch of real, actual content files turned up something the reference material's existence alone couldn't have predicted: for the specific kind of branching choice the earlier heuristic was built for, the real on-disk table is simply *empty* in every real instance checked. The authoritative mechanism exists and is now implemented correctly, but the actual content produced with it never populated the table for this particular case — meaning the literal, byte-for-byte "correct" behavior (fall through to a single hard-coded default choice) would have been indistinguishable, from the data alone, from silently always picking the same branch regardless of which one was actually appropriate. Rather than trust an unverifiable literal reading over a heuristic that had already been confirmed correct through direct, repeated live testing, the old heuristic was kept in place specifically for that one case — clearly documented as a deliberate fallback, not a leftover — while every other, genuinely populated case now uses the real mechanism outright. Ground truth is worth a great deal, but only as far as the real data actually goes; past that point, evidence from direct observation still wins.

## Exhausting every hypothesis, and what it means when they all come back clean

The stride-length finding above (see "When the numbers run out, build a way to actually see it") left one open question: whether the wrong stride length came from how the affected joints' rotations *combine* on the way to a final pose, rather than the recorded rotation values themselves. That turned into a genuinely thorough elimination pass, worth walking through because the ending is more interesting than any single step.

First, an alternate, independently-confirmed way of combining a bone's rest orientation with its animated rotation was tested live, on both the resting stance and an active walk. It changed nothing, visibly, either way. That result could easily have been dismissed as "the toggle probably isn't working" — so it was checked directly first: the control that flips it was confirmed to be registering correctly, over and over, a clean real signal rather than a suspicious silence. The actual explanation turned out to be simpler and more interesting: reading the real per-joint correction values directly out of the character's own rig data for the affected limb showed every single one of them sitting at exactly zero. With nothing to correct, two different formulas for applying a correction necessarily produce the identical result — not a coincidence, a mathematical certainty. The alternate formula was never going to matter here, and now there's proof of exactly why, rather than a vague "we tried it and nothing happened."

Next, real bone length was checked again, this time across a full active walk cycle rather than only at rest — a segment's length in the real world should never change no matter how a joint rotates, so any deviation would mean actual stretching, a real and different kind of defect. It stayed perfectly, exactly constant at every single sampled moment. Then the clip actually being played was cross-checked against every other real reference to the same content across the entire animation library, confirming it really is the standard, shared default — not an unusually energetic variant mistakenly picked up somewhere upstream.

The most conclusive check reused a capability built during an entirely earlier, unrelated investigation: an independent, general-purpose 3D application, fed nothing but the already-decoded keyframe numbers, asked to build its own skeleton and play the same clip using its own unrelated hierarchy and animation systems. Getting this working for the newly-affected limb surfaced a real, separate bug worth being honest about: a subtle naming-case mismatch between two different parts of the data being handed to that external application meant most of the limb's own real motion was silently never applied at all during import — a quiet, easy-to-miss failure mode where "no error was raised" gets mistaken for "everything worked." Once found and fixed, the real test finally ran cleanly, and the result was about as clear as this kind of independent validation gets: bone for bone, frame for frame, the external application's own from-scratch computation matched this project's own values essentially exactly.

Taken together — an identity correction ruling out the composition formula mathematically, perfectly rigid bone lengths, the correct clip confirmed, and now an entirely independent implementation agreeing almost exactly — every concrete, checkable hypothesis for where a stride-length bug could hide in this project's own code has been tested and closed off clean. That's a real, if slightly unusual, kind of conclusion: not "found it, fixed it," but "checked everything checkable, and it's very likely not here at all." The recorded animation data, played back faithfully and combined correctly, genuinely contains this range of motion. Wherever the real difference from the original game actually comes from, the evidence now points away from this project's own reimplementation of the math — which is itself valuable, hard-won information, not a dead end.

One live counter-theory is worth recording too, since it was reasonable and worth checking seriously rather than dismissing: could an already-known, separate defect in the character's resting pose be somehow corrupting the walk cycle by feeding it a bad starting point? Checked directly against the independent cross-check above: neither this project's own system nor the external application it was compared against carries any memory of a "previous" pose between frames at all — every single frame is computed completely fresh, straight from the recorded clip data and the rig's own rest data, with nothing carried over from whatever was on screen a moment earlier. The external application's own version was built entirely from scratch, with zero awareness of the resting-pose defect, and still reproduced the identical result. That's fairly direct evidence against a carried-over-pose explanation for this particular symptom — though it did surface a real, separate, genuinely unimplemented piece of the original system (a real transition/blending layer that smooths entry into a new motion, confirmed to exist in genuine reference material but not yet built here) worth keeping in mind for later, on its own merits, not as an explanation for this specific defect.

## What a deep archive of a platform's own original development tools looks like from the outside

Genuine historical reference material for this platform doesn't only include the game client itself — it includes a real, substantial set of the original internal tools the platform's own developers used to build their content in the first place: dedicated editors for animation state machines, particle effects, terrain, lighting, quests, shaders, and more, plus at least one general-purpose viewer for the platform's own raw data-container format. None of this was expected going in; finding it changed how a couple of open questions got approached.

The practical challenge with material like this isn't reading it — it's finding the right few files inside tens of thousands without downloading gigabytes of unrelated content first. The approach that worked: fetch just the repository's own file listing as plain text first (a single lightweight operation), search that listing locally for anything relevant, and only then pull the actual content of the specific files that matter. That turned an unwieldy, sprawling archive into something that could be searched and mined in seconds rather than minutes, and made it practical to come back to repeatedly over the course of one investigation rather than committing to one big up-front download.

A real, honest decision followed from what was found: one of those original tools is a dedicated animation-authoring application — plausibly the single most directly relevant real reference this project could have access to for the questions being asked. Getting it running directly, rather than just reading its source, was seriously considered. It wasn't attempted. The tool's own build instructions are explicit that it only compiles against tooling roughly a decade older than what's already set up for this project, and only one specific piece of that historical toolchain is even confirmed to build cleanly today — not necessarily the specific application in question. Chasing down and installing an old, specific toolchain purely to get one more reference view, when the source itself was already sitting there readable, was judged not worth the real time cost against everything else waiting to be investigated. Reading the relevant real source directly, without ever launching the tool itself, was still immediately useful — see the previous section on the content-selection format above for exactly what that turned up.

There's a limit worth being honest about here too: having access to genuine original material, and having spent real time working through a meaningful slice of it, is not the same as being any kind of authority on how thoroughly this platform's client has been examined by others over the years — plenty of that work has surely happened elsewhere, out of view. What can be said plainly is narrower and still worth saying: a real, working understanding of this specific animation pipeline has been built here, tested against genuine reference material and cross-validated independently more than once, documented as it went rather than after the fact. If anyone reading this has gone further, or knows something that would fill in a remaining gap, that's exactly the kind of outside knowledge a project like this benefits from and doesn't have any other way to reach.

## Automating a visual A/B test without touching the keyboard — and a near-miss that changed the approach

A resting-pose investigation needed the same visual comparison run repeatedly, each time with one small internal setting flipped, so the results could be compared side by side. Doing this by hand — press a key, wait, take a screenshot, press it again — works, but doesn't scale past a couple of comparisons and depends on a person being at the keyboard for each one.

The first instinct was to automate the keypresses themselves: bring the application's window to the front programmatically, then send it simulated keystrokes. That attempt was abandoned within seconds of trying it. The window-focusing call reported success, but it had actually activated a *different* window — this project's own development environment, not the application being tested — meaning the simulated keystrokes could have landed anywhere, typed into anything with a text field. Nothing was actually damaged this time, confirmed by checking immediately afterward, but the near-miss made the underlying problem clear: reliably identifying *which* window is the right one to send input to, from an external script, on a machine also running other active work, isn't something to trust with real keystrokes.

The fix wasn't a more careful version of the same idea — it was a different one. The application already had a set of debug toggles driven by keyboard input during interactive use. Rather than simulating the keyboard, a small command-line option was added that drives those exact same internal switches directly, timed automatically instead of waiting on a key press. Same code path, same effect, zero simulated input, and no dependency on which window happens to have focus. It's also just better tooling on its own merits — the automated version is reproducible and scriptable in a way a human pressing keys never fully is.

## Two more resting-pose hypotheses closed out, and a wrong assumption caught along the way

With that automated comparison tool in hand, two more candidate explanations for the resting-pose difference could be tested cleanly rather than eyeballed. Both came back negative, and each came with a mechanical reason why, not just "still doesn't look right."

The first candidate was a specific per-joint correction value, one of three that combine to produce a bone's final orientation. It had looked like a real, plausible lever — a value that, unlike its counterpart on the legs (where it's exactly zero), genuinely varies for the arms. Once actually measured directly, though, it turned out to be small enough to be visually meaningless — a fraction of a degree in practice, nowhere near large enough to swing a limb from resting at the side to held out to the front. A real, non-zero number, just not a big one; a good reminder that "not exactly zero" and "large enough to matter" are different claims, worth checking separately.

The second candidate was the order in which those correction values combine — there's more than one mathematically reasonable way to compose three rotations together, and the correct order hadn't been independently confirmed for this specific pose. Every plausible ordering was swept automatically and compared side by side. All of them produced essentially the same result. The reason became clear once the actual magnitudes were in hand: one of the three values involved is large — close to a half-turn — while the animated motion layered on top of it is comparatively small. Reordering a small rotation relative to a dominant large one barely moves the end result, so no ordering was ever going to look meaningfully different.

The more interesting finding was a wrong assumption sitting underneath both tests. The working mental model going in was that "resting" meant a literal, unanimated reference pose — the raw skeleton data with nothing layered on top. Checking the actual behavior directly showed that isn't true: the character is always playing a real, subtle idle animation, even standing perfectly still, not sitting in a bare unanimated state at all. Both hypotheses above were tested rigorously against the *wrong* starting assumption before that was caught — which didn't invalidate the results (the measurements and the sweep are still valid, real evidence), but it does reframe what's actually left to explain: not "what does the bind pose look like," but "why does the real, already-animated resting motion still read as displaced."

## Reading the platform's own original production code, and what it did and didn't explain

Genuine leaked source material for this platform's actual client-side code later became available — not editor tooling built around the content pipeline (see the archive described above), but the literal compiled logic the original game itself uses at runtime to compute a character's pose. This let several standing assumptions be checked against real ground truth instead of continued inference from decoded file data alone.

The formula this project already uses to combine a bone's three rest-orientation correction values with its animated rotation turned out to be character-for-character identical to the platform's own real one. That's a strong, independent confirmation of a piece of math that had already survived a lot of scrutiny — but, importantly, it didn't by itself explain the resting-pose difference, since that mismatch was already known (from the side-by-side comparison described above) to live somewhere other than this specific formula. The correction values themselves were separately confirmed as genuine, deliberate rig data authored in the original 3D animation tool this platform's own artists used, not decode noise — closing off any lingering possibility that discarding them might be the right move.

A recursive content-selection format decoded much earlier (see "A flat lookup table turned out to be the wrong mental model entirely," above) turned out to have one more real layer than previously modeled once checked against the platform's own code: what had looked like a simple mood-name lookup is actually a set of many small ambient variations — the character idly shifting weight, glancing around, checking a device, and similar small flourishes — a genuinely richer piece of the original design, surfaced here mostly because it needed ruling out as a contributor to the specific defect being chased, not because it changed which clip actually gets played. A separate, suspected secondary motion-blending layer (mentioned as a real, confirmed-to-exist gap in an earlier section) was checked directly against the platform's own registration logic and ruled out as the source of this particular symptom: it only activates when a specific, deliberate gesture is actually queued, and correctly stays dormant the rest of the time — exactly matching how this project's own reimplementation already behaves when nothing is queued.

One genuinely new, precisely measured fact came out of this pass, and it's the most important result of the whole session: pulling every single recorded keyframe across the character's real, always-playing idle motion and checking the total range of motion it covers for the affected limb found it tops out at a few tens of degrees at most, across the *entire* clip, not just the currently-visible moment. That's nowhere near the roughly quarter-turn a shoulder would need to travel to get from this project's own computed rest configuration to a natural at-the-sides stance. Every mechanism checked this pass — the core formula, the correction values, how they combine, the real per-character context (mood, held item, combat/sitting/other state flags) actually driving which animation gets selected, and the secondary blending layer — is now confirmed either correct or not the cause. What's left is a real, precisely-quantified fact with no identified explanation: the motion is too small, and nothing found so far explains why.

## Exhausting the skeleton file format, and a real decode bug found and fixed along the way

Fresh, deliberate side/back/front comparison screenshots of the original game, taken specifically for this investigation, confirmed something worth stating plainly: the original's "resting" stance is itself a real, continuous animation loop with its own small ambient gestures — the character taps a foot, glances around, rubs its chin — not a static pose at all. But regardless of which specific gesture happens to be playing in a given screenshot, the arm and leg placement reads as consistently different from this project's own rendering. That rules out "the two screenshots just happened to catch different moments of the same correct loop" as an explanation — the difference is structural, not timing.

That prompted going back to the raw skeleton file format — the one holding each bone's base rest position and its correction values — and, this time, reading the platform's own original file-loading code for it directly, line by line, rather than continuing to work from a partial understanding built up from reverse-engineered file dumps alone. The result was exhaustive rather than incremental: the real format can contain exactly a handful of distinct pieces of per-bone data, and every single one of them is already read and used by this project — with one specific exception, a value the platform's own original code itself discards immediately after reading it (a comment in the real source says as much directly), matching this project's own prior decision not to use it either. There is nothing left unread in this specific file format. It's now eliminated as a possible location for whatever's missing, not just deprioritized.

Reading that same original code raised a natural adjacent question: what does a bone that a specific animation clip doesn't explicitly cover with its own motion data actually do at playback time? Reading the real answer directly turned up a genuine, previously-wrong assumption baked into this project: such a bone isn't simply "unchanged from its rest position" (the assumption quietly made and never actually checked against source). The real file format stores an actual, fixed, deliberately-authored resting value for that specific bone in that specific clip — a real piece of data, structurally distinct from the animated-motion curves most bones carry, living in a part of the file this project had never read at all.

That gap was closed directly: the previously-unread data was located, decoded (reusing the exact same quantized-rotation math already trusted for the file's animated motion curves, since it turned out to use an identical encoding), and wired into the pose calculation for exactly the bones that need it. Verified against real recorded values pulled straight from real game content files. New automated test coverage was added confirming it round-trips correctly against real files, not just synthetic data. Tested live, end to end, against a running server.

It works exactly as intended — a genuine, previously-missing piece of real per-character animation data, now correctly restored where before it was silently defaulting to the wrong assumption. **It did not fix the resting-pose difference.** The actual values this newly-restored data supplies are, like the animated motion measured in the previous section, only a few tens of degrees at most — real, correct, present in the file for the first time in this project's rendering, and still nowhere near the missing quarter-turn this specific defect needs.

## Where this leaves the resting-pose defect

Between the two investigations above, every per-clip animation data source either of the two relevant file formats can contain has now been read, checked directly against the platform's own original production code, and — everywhere a real gap actually existed — fixed. That's a stronger conclusion than "we've tried a lot of things": it's closer to "we've now read everything there is to read in these files, twice over, once from decoded dumps and once from the platform's own real loading code, and none of it, alone or combined, accounts for the difference."

What's left points outside per-clip animation data entirely: whether this project's own understanding of a character's base rest configuration — independent of any specific clip, the thing every animation is defined *relative to* — is itself subtly wrong in a way none of the checks above would have caught; whether the real game applies some further override at a level this investigation hasn't yet located (a template-level default, an engine-side convention specific to the "at rest, nothing queued" state, something structural rather than data-driven); or a difference not yet identified at all. Each remaining candidate has a concrete next check, and none of them has been tried yet.

This is, by a clear margin, the most thoroughly investigated open defect in this project's history — many separate sessions, several independently-designed hypotheses each tested to a clean conclusion rather than abandoned partway, cross-validated more than once against an entirely independent third-party implementation, and now checked against the platform's own genuine original source code directly rather than inferred secondhand. The internally-visible leads are, as of this writing, exhausted. If anyone reading this has real hands-on knowledge of this platform's animation pipeline, its rest-pose conventions, or its original content-authoring tools, and recognizes this specific symptom — arms held away from the body rather than resting at the sides, present regardless of which idle gesture is playing, unexplained by any per-clip animation data — that's exactly the kind of outside knowledge this project has no other way to reach. Genuinely welcome, and would be credited.

## One last isolation check, and where this actually stands

With every per-clip animation data source exhausted, one clean check remained: strip animation out of the equation entirely and look directly at the raw, computed base pose the character sits in before any clip is ever applied — the thing everything else is layered on top of — from every angle, not just one. Doing that settled a real, previously-open question: it's a genuine, unambiguous T-pose, arms held fully horizontal.

That's a clarifying result, not a discouraging one. A T-pose base reference is the standard, near-universal convention for a skinned character rig — this project's own base pose is very likely correct exactly as it stands, not a defect needing a fix. The real client never displays that literal base pose either; a character is always animated, even standing still. Which means the entire job of turning a T-pose into a natural at-the-sides stance necessarily has to come from animation data layered on top of it — and every real source of that data this project can read, checked exhaustively, supplies only roughly a third of the rotation actually needed.

That narrows things to one specific, well-defined remaining question instead of an open-ended one: either this project is resolving to the wrong specific clip for this exact situation, or the real client applies some additional, always-on base layer beneath the visible idle motion that hasn't been identified. Distinguishing between those two needs a form of investigation this project has used successfully before, just not yet pointed at this specific question — directly observing the real client's own behavior at the machine-code level, rather than working from decoded file data.
